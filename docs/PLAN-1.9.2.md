# 1.9.2 方案（第 2–4 项已在 1.9.2 发布，见 `CHANGELOG-1.9.2.md`；第 1 项 F9b 记录，下一版做）

## 1. 首页三个模块不再用颜色区分（2026-11-09 对齐，Figma「方案 · 1.9.1」F9b）

来源：1.9.1 装上后，首页蓝 / 紫 / 橙三个实心图标块显得“玩具感”，不像专业团队的设计。

先后看了三版：F9（全中性）→ **F9b（选定）** → F9b 的对对风格图标（没采用，已在 Figma 里调淡标注）。

**选定：F9b 白色卡片 + 扁平插画图标（多邻国方向）**
- 卡片整块白底、2px Swan 边框，去掉灰色标题条；模块标题 17px Black。
- 标题前是 28px 扁平插画：纸张用中性色（跟着深色变量），每个只有一个带底边的小圆章 / 印章用品牌色——新比较 Feather 绿“＋”、往来稿 Macaw 蓝“⇄”、模板 Fox 橙印章。只作插画，不代表含义。
- 页签：选中 = Macaw 蓝文字 + 3px 蓝色下划线，下面一条 2px Swan 底线；计数是灰色文字，不加底色。
- 卡片本身不做悬停（不能点）；里面的行悬停 = Side 浅灰底、圆角 12。
- 空卡片：72px 插画 + 一句标题 + 一句说明 + 一个带 4px 底边的次要按钮。
- 设计系统：去掉变量 `beetle-lip`、`fox-lip` 和规范里“首页模块色”一条；组件库加 `illo/new`、`illo/lib`、`illo/tpl`，更新 ModuleCard、Tabs。

**没采用：对对风格图标**（对对本人 + 纸飞机 + 印章；三个小对对）——32px 里细节太多、描边画法不统一、和底栏的对对抢戏。

## 2. 首次审阅决定卡顿：提示音不再用 AudioContext（2026-11-09，已修，未发版）

来源：macOS 本机实测（隔离配置、合成 3,000 段 Word、提示音开）：第一次按 R 时 `new AudioContext()` 耗时 178–253ms，对应 209–320ms 的主线程长任务。

- 修法：`lib/chime.ts` 把四种提示音在 JS 里直接算成很短的 WAV（同样的正弦波、音量包络、时长），用 `<audio>` 播放；加载、解码、开音频设备都在媒体线程里异步做。全程不构造 AudioContext。
- 提示音打开时，进入修订审阅就在空闲时间准备好四个 `<audio>`（只算 WAV、建元素，不开设备）；提示音关闭时什么都不创建。
- 测试：`scripts/test-chime.mjs`（WAV 格式、时长、音高、音量与原版一致；源码里没有 AudioContext）；`scripts/perf-review-chime.cjs`（3 轮冷启动 × 12 次 R：AudioContext 构造次数、`play()` 主线程耗时、长任务、界面反馈、文件更新、Word 内容核对）。
- Linux / xvfb 结果：修前 AudioContext 35–54ms、首次决定长任务 65–92ms；修后 AudioContext 0 次、`play()` 同步 ≤ 1ms、进入修订审阅无长任务。首次决定仍偶有 50–68ms 的长任务，关掉提示音同样出现（大文档首次重排，ChangeMap 读 scrollHeight 触发的布局），与音频无关；macOS 上需要用安装包按 `perf-review-chime.cjs` 复测确认 ≤ 50ms。

## 3. 性能回归基线（2026-11-09）

`scripts/perf-baseline-191.cjs`，夹具 `make-perf-review-3000.py`、`make-perf-pdf-120.py`（全部虚构）：
- modes：3,000 段 Word 纯文本 / 修订审阅 / 富文本切 20 轮，首次纯文本单独记，热切换参考 < 100ms（macOS），每 5 轮 GC 后 JS 堆不持续增长。
- pdf：两份 120 页 PDF 图像模式，约 5 页时停止：停止反馈、停止后 700ms / 2s 页数不涨、继续后 120 页无漏无重、长任务、内存峰值（合计 + 渲染进程）。
- Linux / xvfb 参考：首次纯文本 919ms，热切换纯文本 p50 162、修订审阅 128、富文本 54ms；堆 36 → 58 → 57 → 58 → 57 MiB。PDF 停止反馈 235ms，停止后不再增长，继续 20.1s 完成 120 页（120 页不重复）。Linux 无显卡渲染约为 macOS 实测的 2 倍，阈值用 `SWITCH_MAX` / `LONG_MAX` 调。

## 4. 快速审阅后立即离开：审阅稿漏写（P1）、往来稿轮次摘要漏写（P2）（2026-11-09，已修，未发版）

来源：macOS 安装版实测（合成 3,000 段、三版本往来稿）：V1 → V2 快速按 R 40 次后立即退出 / 新建比较 / 切到 V2 → V3，决定都持久化了，但旧审阅稿没更新；轮次摘要 decided 0。

**审阅稿（`lib/draft/client.ts`）**
- 离开界面时实例不再丢掉待写的决定：转到后台立刻写完最后一批（不等 0.25 秒合并），Worker 生成在途的结果照样提交。
- 同一份审阅稿（同一对文件）的“生成 + 写盘”跨实例按顺序排队；后台的旧实例发现这一对文件又被打开了，就不用旧快照写，交给新实例用最新决定再写一次——旧快照不会盖掉新决定。任务只写自己这一对文件登记的审阅稿路径。
- 有还没写进去的决定时，状态片不显示“已保存”，完成页不把审阅稿当成可以发送。
- 写不进去（Word 占用、被改过、移走、文件夹写不进、出错）：离开界面后弹窗写明哪份审阅稿、几个决定没写进去、为什么、怎么补；记一笔“待补写”（设置 `draft-pending`）。
- 退出 / 关窗：主进程先问渲染进程，把往来稿摘要和审阅稿里剩下的决定写完（最多等 5 秒）再关；写不完时问“先不退出 / 仍然退出”，并记“待补写”。渲染进程 8 秒不回话照常关。
- 重启：弹窗列出上次没写完的审阅稿；再打开这一对文件时自动补写，写好后清掉记录。
- 不是缩短防抖，也没有在主线程同步写盘（仍在 Worker 生成、主进程原子写）。

**往来稿轮次摘要（`App.tsx`）**
- 待写的摘要按“往来稿 + 版本对”记；换版本对、离开往来稿、新建比较、退出时立刻写掉，不再被新版本对取消。
- 只在决定确实属于这一对版本时才写（换版本时新结果还没出来，不会把旧决定记到新的一轮上）。与是否生成审阅稿无关。

**测试**
- `scripts/test-draft-lifecycle.mjs`：12 项（新增：离开时最后一批立即写入；旧快照不盖新决定；退出写不进去时上报并登记、重开后补写）。
- `scripts/e2e-192-leave.cjs`：退出 / 新建比较 / 切版本 × 防抖未执行 / Worker 生成在途 / 主进程保存已提交（测试钩子：`__ddDraftHooks`、`global.__ddSaveDelay`、`__ddRoundDelay`），核对 40 个持久化决定和审阅稿“接受全部修订”后的文字、审阅人修订数与不离开时写出的参考稿完全一致；Word 占用时的提示、退出提示、重启提示与补写；两版本两份审阅稿不串写；旧保存未完成时切回改一处，最终文件是最新决定；不生成审阅稿时轮次摘要 40 条、重启后条款历史显示。
- Linux / xvfb：全部通过。按 R 40 次期间最长主线程任务 0–80ms（修前同样 0–64ms）；离开等待：切版本 0.57–0.91s（修前 0.88s，主要是比较新版本）、新建比较 0.09–0.2s（修前 0.14s）；退出会先写完审阅稿：0.36–0.77s（主进程钩子卡 2.5 秒时 2.5s；修前 0.06s 但会漏写）。
