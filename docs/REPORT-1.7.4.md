- 时间都在同一台机器上前后对比。云端机器比两位评测人的机器慢得多，绝对值不能和评测报告直接比。
- 每组至少 3 轮，取中位数，括号里是最小–最大。另跑 1 轮包装 `querySelector` / `querySelectorAll` 统计调用次数；包装本身有开销，所以计时用的是不包装的那 3 轮。
- 时间口径：
  - elapsed：点击到目标视图出现，再加两帧。

  - P95 / max gap：窗口内 requestAnimationFrame 的帧间隔。
- “刚出结果”：结果出现后的 3 秒窗口；另外单测结果一出现就点“下一处”、点地图。“稳定后”：切回富文本后再等 1.5 秒，然后连按 5 次“下一处”、点地图、滚动 4 秒。

## 1. [P1] 中文矢量 PDF 漏报金额 / 期限，显示“全部无差异”——已复现，已修复

**复现**

- 用 Windows 评测的原文件 `vector-pdf-30-a/b.pdf`（第 7/14/21/28 页改了金额和期限）。1.7.3 的富文本是 0 处差异，图像模式 30 页都是“无差异”。
- 自制的 `cn-mix` 夹具（正文嵌入字体，金额 / 期限 / 服务期限三行用不嵌入的 STSong-Light）结果相同：三行在富文本里根本不出现，图像里这三行是空白。
- 原始数据：`perf-1.7.4/cjk-before/`（1.7.3，10 项失败）、`perf-1.7.4/cjk-after/`。

**定位**（逐层排查，先排除了字体缺失）

- 文件层：中文字体“Heiti”没有嵌入，编码是 `UniGB-UTF16-H`，属于预置 CMap 编码。
- 字体加载层：用 1.7.3 的 pdf.js 配置检查操作列表，这个字体返回的是加载错误，不是字体对象。错误信息是 “Ensure that the `cMapUrl` and `cMapPacked` API parameters are provided”。
- 文本提取层：同一页 1.7.3 只提取到 31 个文本项，补上 CMap 后是 191 个，中文行全部丢失。
- 渲染层：同一个字体对象加载失败，这些行也画不出来，所以图像模式同样看不到改动。
- 比较层：两边都“看不见”这些行，比较引擎本身没有问题。

**根因**：应用没有把 pdf.js 需要的预置 CMap 和标准字体数据打包，也没有传给 `getDocument`。不是系统缺字体：Linux 上补上 CMap 之后，仍然提示找不到 Heiti 系统字体，但已经能正确回退并渲染。

**改动**

- `vite.config.mjs`：构建时把 `pdfjs-dist/cmaps`（169 个）和 `standard_fonts` 复制到 `dist/pdfjs/`；`pdf.ts` 的 `openPdf` 传入 `cMapUrl`、`cMapPacked`、`standardFontDataUrl`。已确认 Windows 和 mac 安装包的 asar 里都有这 169 个文件。
- 读取时检查每一段文字：字体加载失败，或者字形没有 Unicode 映射，就记成“读取问题”，记下页码、段数和类型。
- 有读取问题时，结果页顶部出现红色警告，写清是哪份文档、第几页、几段读不出，并说明“这些内容没有参与比较，‘没有差异’不代表这些地方相同”。警告里给出两个入口：“用其他阅读器打开”，以及字形本身没有编码时“改用 OCR 文本比较”。
- “比较范围”的“未比较”里列出这些页。图像模式里，这些页不再标“无差异”，改标“有文字没能读出，可能缺字，未必相同”。
- 新增回归夹具 `test/fixtures/cjk-pdf/`，期望结果写在其中的 README。

**回归**（`scripts/e2e-174-cjk.cjs`，21 项全部通过）

|---|---|---|
| vector-pdf-30（Windows 原文件） | 0 处；图像无差异页 | **8 处**；图像差异页正好是 7/14/21/28 |
| cn-mix A↔B | 0 处，三行改动全部漏掉 | 4 处，120,000→198,000、30→15、十二→二十四 都能找到 |

## 2. [P1] 差异地图大量 DOM 查询——已复现，已修复

**复现**：word-3000（1712 处差异）在 1.7.3 上，切回富文本一次要 5,145 次 `querySelector`，累计约 1.57 秒；连按 5 次“下一处”要 12,013 次，累计约 3.5 秒。与 Windows 评测的约 6,849 次 / 0.85 秒、mac 的约 1.5 秒累计是同一个问题。

**根因**（三点叠加）

1. 测量时对每一处差异都在整棵正文里执行 `querySelector([data-cid])`，找不到时再查一次 `[data-row]`，次数 = 差异数 × 1–2。
2. effect 的依赖 `dep` 是调用方每次渲染新建的数组，所以任何一次重渲染都会拆掉 effect 再重建。选中一处差异、悬停都会触发，然后在 60 毫秒和 600 毫秒各量一遍，ResizeObserver 再补一遍。
3. 富文本没有 `content-visibility`，只能逐个精确测量；而且每次切回来都从头再量。

**改动**（`ChangeMap.tsx`）

- 一次 `querySelectorAll('[data-cid],[data-row],[data-rows]')` 建好 id → 元素、行号 → 元素的索引。
- 差异超过 200 处（画成密度条）时只量每一行的第一格，量的次数从“差异数”降到“行数”。
- `dep` 按元素逐个比较，内容没变就不重跑。去掉 60 / 600 毫秒两次固定重测，只在 ResizeObserver 报告尺寸真的变化时再量（防抖 120 毫秒）。
- 按“差异列表 + 版面尺寸 + 依赖”缓存刻度，切回同一个视图直接用。
- 正文按需挂载后，没挂上的行在占位块里按行号比例估算位置。

| 切回富文本：查询次数 / 累计 | 5,145 / 1,574 ms | 6 / 8 ms | 22 / 2.6 ms |

## 3. [P2] 富文本整篇挂载——已复现，已改为按需挂载

**复现**：word-3000 在 1.7.3 的富文本有 29,887 个元素；切回富文本是整篇重建（longest 1.16 秒）。3000 段全文改写的用例（mac 评测里切换超时）在 1.7.3 上：首次出结果主线程约 2.5 分钟无响应，切回富文本又约 2 分钟无响应，页面达到 213,228 个元素（`perf-1.7.4/rewrite/probe-173.json`）。

**改动**（`RichView.tsx`）

- 按行号每 60 行分成一块。只挂视口往上一屏、往下两屏范围内的块，其余换成同样高度的占位，占位上带 `data-rows`，供地图估算位置。
- 量过的块高度按“块内容 + 宽度 + 对齐状态”缓存；没量过的块按字数估算。高度变化时靠浏览器的滚动锚定，保持视口内容不动。
- 少于 360 个条目的文档仍整篇挂载，行为与以前完全一样。
- 以下几种情况，相关块始终挂着：跳转目标、选中差异所在的块、对齐所在的块、选区经过的块（选区两端之间全部挂上）。全选时挂上全文，取消选区后恢复按需挂载。
- 远距离跳转改为直接跳过去，两帧后再校正一次，避免平滑滚动途中挂载内容、高度变化导致落点偏移。
- 每一行做成 `React.memo` 组件：选中别的差异、鼠标悬停时，其他行不再重新渲染。1.7.3 每次悬停都会重渲染 3000 行。

**分开测量**（同第 2 节表格，“只改地图”与“地图 + 正文”两列的差就是正文改动的效果）

| word-3000 | 1.7.3 | 只改地图 | 地图 + 正文 |
|---|---|---|---|
| 富文本元素数 | 29,887 | 29,887 | **3,996** |
| 切回富文本 elapsed / 最长任务 | 3296 / 1162 ms | 1283 / 604 | **158 / 0** |
| 稳定后 JS 堆（强制 GC 后） | 148 MB | 148 | **83** |
| 渲染进程常驻内存 | 756 MB | 754 | **474** |
| 稳定后滚动 4 秒：P95 / 最大帧间隔 | 16.7 / 33 ms | 16.8 / 17 | 16.8 / 50 |

- word-1250：元素 14,387 → 3,909，堆 70 → 43 MB；sparse-2000：13,670 → 1,243，堆 175 → 107 MB。
- 3000 段全文改写（15,000 处差异）在 1.7.4 上：每次切换都在 10 秒采样间隔内完成，富文本 7,577 个元素。另跑 1 轮基准：首次出结果 5.3 秒，切回富文本 680 ms。

**功能回归**（`scripts/e2e-174-view.cjs`，17 项全部通过）

- 只挂载视口附近。
- 下一处、上一处、点清单 60% 处、点地图 80% 处：都落在视口里，视口里是真实内容。
- 滚到 40% 停 1.5 秒，视口里的行不漂移；能滚到最后一行。
- 从第 2 行选到第 1559 行：中间的行被挂上，并包含在选区里。全选能选到最后一行；取消选区后恢复按需挂载。
- 点词对齐两侧正常；只看有变化的段落时折叠和跳转正常；纯文本 → 富文本 158 ms。
- 100 段的文档整篇挂载、没有占位，地图 56 条刻度。
- 修订审阅的接受 / 拒绝、批量操作和撤销仍由 `e2e-173.cjs` 覆盖（全部通过）。

**剩余限制**

- 纯文本（3000 段约 3.7 万个元素）和修订审阅（约 1.9 万个）这次没有改，仍然整篇挂载。全文改写的极端用例里，修订审阅约 19 万个元素，切过去仍要几秒。
- 浏览器自带的页内查找（Ctrl/⌘+F）只能找到已挂载的段落。DocDiff 本身没有提供页内查找。

## 4. [P2] 图像比较未完成就显示“全部 30 页已比较”——已复现，已修复

**复现**：1.7.3 在 vector-pdf-30 比到第 8 页时，同屏出现“比较了全部 30 页”和“正在比对第 8/30 页”（`perf-1.7.4/progress/` 有 1.7.4 的逐帧采样）。原因是 `RangeLine` 只看所选范围，不看任务状态。

**改动**

- 图像比较的状态里分开记“范围共几页 / 已完成几页 / 是否全部完成 / 停止 / 出错”。新增“停止比较”。停止或出错后保留已比较的页，“继续比较”或“重试”从下一页接着比。
- 范围那一行分五种状态：

| 状态 | 中文 | 英文 |
|---|---|---|
| 进行中 | 比较范围：全部 30 页；已完成 8/30 页 | Comparing all 30 pages: 8/30 pages done |
| 完成 | 全部 30 页已比较 / 只比较了第 a–b 页，共 n 页；其余页面没有比较 | All 30 pages compared |
| 停止 | 已停止：比较范围 全部 30 页，已完成 9/30 页，还有 21 页没有比较 | Stopped while comparing … |
| 出错 | 比较出错停止：……已完成 11/30 页，还有 19 页没有比较 | Stopped by an error … |
| OCR 开始前 / 中 / 取消 | 比较范围：全部 3 页 / ……；已识别 1/6 页（两份文档合计）/ 已取消识别：……没有生成比较结果 | 对应英文 |

- 检查器摘要在没比完时加“（已完成 x/n 页）”。“每一页在视觉上都没有发现差异”只在全部完成后才显示，否则改为“已比较的 x 页没有发现差异，还有 y 页没有比较”。

**回归**（`scripts/e2e-174-progress.cjs`，16 项全部通过）

- 每 50 ms 采样，比较进行中从没出现“全部 30 页已比较”。
- 停止后：已完成数 + 未完成数 = 30，且等于列表里的页数。继续比较后 30 页按顺序、没有重复，差异页正好是 7/14/21/28。
- 模拟第 12 页失败：显示已完成 11/30，重试后补齐。
- 英文文案、OCR 开始前 / 识别中 / 取消 / 完成四种状态都检查过。
- 1.7.3 已有的大文件范围测试（450/452 页、只比 301–330 页）在 `e2e-173.cjs` 中全部通过。

## 5. 内存：多轮“打开 → 比较 → 切换模式 → 新建比较”

**脚本**：`scripts/memory-174.cjs`。每轮依次比较 word-3000、vector-pdf-30（含图像）、word-1250（含图像）、pdf-30 扫描件（含图像），循环往复。每轮记录渲染进程常驻内存、JS 堆、强制 GC 后的堆、页面图片缓存（组数 / 页数 / 存活图片地址数和大小）、元素数。数据在 `perf-1.7.4/memory/`。

**顺带发现并修复的问题**

1. 图像比较做到一半就切走时，这一轮已经生成的页面图片（blob URL）没有释放。现在切走、停止被替换、出错放弃时都会释放。
2. Word / TXT 排版出来的 PDF 缓存没有上限，现在只留 4 份。“新建比较”时清空页面缓存。
3. 新建比较后，侧栏显示上一组文档的差异数（1.7.3 实测：扫描件旁边显示“纯文本 1712 / 712”）。纯文本和 OCR 的旧结果没有按文档区分，切过去会短暂闪出旧结果。现在只交出同一组文档的结果。
4. 换文档后进入图像模式，第一帧会显示上一组的页面和“全部 n 页已比较”。1.7.3 的多轮测试里，这会让图像模式像是“瞬间完成”（0.6 秒），实际并没有重新比较。

**结果**（8 轮，强制 GC 后的 JS 堆，同一组文件出现的两轮）

| 文件 | 1.7.3 | 1.7.4 |
|---|---|---|
| word-3000 | 130.3 / 131.4 MB | 85.7 / 82.8 MB |
| vector-pdf-30 | 50.7 / 51.7 | 18.5 / 18.9 |
| word-1250 | 63.5 / 63.7 | 42.7 / 42.8 |
| pdf-30 扫描件 | 40.7 / 41.2 | 27.2 / 27.3 |

- 1.7.4 的 JS 堆和页面图片缓存不随轮数增长：16 轮里 word-3000 的 GC 后堆依次是 81.7 → 85.1 → 85.3 → 85.4 MB，图片缓存始终只有当前这一组。
- **未解决：渲染进程常驻内存随图像轮次增长。**
  - 1.7.4 跑 16 轮，从 457 MB 涨到 910 MB。
  - 只做文字比较 6 轮：474 → 489 MB，基本不涨。
  - 只做 vector-pdf-30 图像比较 6 轮：328 → 495 MB，每轮约 +30 MB。
  - 改用共享的 pdf.js 工作线程试过，没有改善（已撤回）。
  - JS 堆和图片地址都不涨，说明是原生内存（候选：画布后备内存、解码图片缓存没有归还给系统），原因还没定位。
  - 1.7.3 因为上面第 4 点，同样流程下没有真正重新比较，没法做同口径对比，所以不能说这是 1.7.3 就有的问题，也不能说是 1.7.4 新引入的。
  - **Mac 上没有复现**：Apple M2 上跑同样 8 轮，渲染进程依次为 438 → 464 → 541 → 530 → 541 → 521 → 506 → 495 MB，到顶后回落，GC 后的堆和 Linux 一致（word-3000 为 86.8 / 82.9 MB）。所以增长目前只出现在没有 GPU 的 Linux 环境（xvfb、软件渲染）。Windows 没有测。
  - 列为下一版待查项，建议在 Windows 上用 `memory-174.cjs` 跑 16 轮确认。
